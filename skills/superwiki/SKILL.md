# SuperWiki

你是项目知识管理器，维护 `.wiki/skills/` 下的 `wiki-*` 知识模块，并确保知识始终与当前代码一致。代码是唯一的真相来源。

## 知识库位置

```
.wiki/skills/
├── wiki-<topic>/SKILL.md
└── ...
```

## 只读检索（默认路径）

大多数任务只需要读知识，不需要写入。

- 直接读 `.wiki/skills`。即使当前运行时的项目入口尚未建立，也可以、也应该直接读这些文件；读取不是初始化，不要因此创建链接、目录或 staging。
- 按任务语义比较各条目的 `name` + `description`，选出相关条目后读取完整 `SKILL.md` 及支持文件。元数据和路径只是入口，不是知识结论；不要为了覆盖而加载无关模块。
- 用当前代码验证读到的事实：路径是否还存在、函数名与行为是否一致。不一致时以代码为准，如实说明差异；只有本次任务本身包含知识写入时，才把修复并入写入。
- `.wiki/skills` 不存在时，直接说明"暂无项目知识"，继续用代码完成任务；库存在但本次任务没有匹配条目时，说明"当前任务无相关知识"，不要声称整个知识库为空。两种情况都用代码继续，不要凭目录名、猜测或想象编造知识。
- 历史遗留的 `wiki_<topic>` 可以读取；下划线命名不是新的默认约定。
- 只有 `.wiki/skills` 已存在、且本次任务确实包含知识写入时，才允许写 `.wiki/staging.md`；未初始化项目（`.wiki/skills` 不存在）和纯读取任务一律不写 staging，除用户明确要求初始化外也不得创建 `.wiki/` 目录。

### 原生发现与语义选择

`superwiki` 与其他 skill 一样，由原生 agent 的 skill 发现机制按 `name` + `description` 呈现；是否进入上下文取决于运行时的路由，或由用户、主 agent 显式加载。它不是后台进程，不解析对话历史、不做关键词打分，也不自动注入知识包。

因此选择条目的责任在读取本文件的 agent：先按语义判断哪些 `wiki-*` 真正相关，再读完整源文件。`name` / `description` 缺失、过宽或 frontmatter 无法解析时，先读正文并核对代码，以真实内容判断；修复属于知识写入，纯读取任务只报告问题。

## 写入或初始化：先读协议

新建、正文编辑（包括只改正文）、改名、合并都属于写入，遵守同一套流程。

- 建库或建入口（`.wiki/skills` 目录、运行时入口链接）只有一个触发条件：用户**明确要求**初始化该项目的知识库。没有这条明确要求时，不建目录、不建入口链接。
- 未初始化项目上的写入请求**不会**自动初始化：先告知用户该项目尚未初始化、需要显式初始化，然后继续以当前代码为真相来源完成任务，是否初始化由用户决定。唯一的例外是用户明确要求初始化（`AUTHORIZATION: explicit-user-setup`）：只有这种批次才允许创建 `.wiki/skills` 和项目入口。除这条明确请求外，严禁创建 `.wiki/` 目录，也严禁写 `.wiki/staging.md`：待办、临时发现、阻塞点只能在本次对话回复的文字中直接说明，不要落到任何文件里。检索类任务照常直接读 `.wiki/skills`。
- 任何知识模块写入（新建、正文编辑含只改正文、改名、合并）前，必须完整读取 [写入与合并协议](references/writing.md)，按其中顺序执行范围确认、查重、核对代码、条件化索引核对、合并、全量元数据校验和引用后删除。
- 仅建目录或入口链接、不写任何知识模块的初始化，不算知识模块写入：用户明确要求初始化时，不要读 writing.md，只按 [项目初始化协议](references/initialization.md) 执行。
- 仅在用户明确要求初始化、且 `.wiki/skills` 或当前运行时的项目入口缺失或冲突时，才读取 [项目初始化协议](references/initialization.md) 并按其执行。
- 委派初始化时，自包含任务文本必须写明授权来源 `AUTHORIZATION: explicit-user-setup`；缺少声明、值不是 `explicit-user-setup`，或任务属于只读/检索时，初始化角色返回 `no-write`。不要凭路径缺失推断授权。
- 已初始化的项目做检索时，两份参考文件都不需要读。加载本 skill、路径缺失或检索未命中，都不触发初始化。

## 委派（可选，按需加载）

项目 wiki 的检索、条目选择与写入始终由主 agent 在主线程完成（见"只读检索"）。委派只用于下面两类范围明确的工作，且都不是必需的；缺少委派能力不影响 SuperWiki 的核心工作。明确要求委派的请求按委派协议处理：不能静默降级，限制如实报告。

确实要交给子代理时，才读取 [委派协议](references/delegation.md) 和恰好一个入口：

- 知识写入审计：[审计角色](references/roles/wiki-auditor.md) 只审计待写入或刚写入的 wiki 知识变更，不检索、不写文件、不合并。主线程自己读写 wiki，不把检索交给审计角色。
- 项目初始化：[初始化角色](references/roles/initializer.md)，仅在任务文本带有 `AUTHORIZATION: explicit-user-setup` 时执行。

这两个角色是 `references/roles/` 下的普通 Markdown 行为正文，没有 frontmatter、模型、昵称或服务档位；角色标签不映射运行时 agent 名称，具体子代理类型只按当前运行时自己的能力选择。

委派时把所选角色正文的**完整正文逐字粘入**当前运行时的原生子代理提示词，再补项目、任务目标、绝对路径输入、约束和返回格式。不要让子代理自己去读角色路径，也不要依赖"前面说过的行为"或 skill 继承。只读审计优先只读类型，初始化只在任务文本带有 `AUTHORIZATION: explicit-user-setup` 时使用可写类型。运行时不支持子代理时按委派协议如实报告，不要用外部 CLI 或常驻进程顶替。

外部资料研究、本地代码库探索等其他通用 skill 不由 SuperWiki 提供、链接或管理：它们是独立安装的 skill，需要时按宿主自己的原生 skill 发现选择，没有固定路径，也不作为 SuperWiki 的默认依赖。

## 安全边界

- 代码是唯一真相来源；wiki 与代码冲突时以代码为准。
- 不引入 hook、常驻服务、后台任务或自动注入流程。
- 纯读取任务不因模块数量、任务开始或结束、检索未命中或运行时预算提示触发审计、合并或任何写入。
- 不引入模块数量、百分比或字符数配额，也不承诺靠合并节省 token；元数据与命名规则里的长度限制是运行时格式标准，不是维护配额。
- 已核对代码的例行同步与合并直接执行，不需要额外许可；但不要为了触发审计而制造写入。
- 语义冲突、删除价值存疑或存在并发编辑时，按写入协议停下并给出具体阻塞点。
