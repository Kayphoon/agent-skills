# 写入与合并协议

本文件是知识写入路径的唯一细节来源。开始任何实际写入前，必须先完整读完本文件：新建模块、普通正文编辑（包括只改正文的编辑）、改名、合并，全都适用。纯读取任务不要读本文件，也不要执行其中任何步骤。

一次连贯的写入批次共用一次检查，但检查必须覆盖该批次最终实际变更的全部元数据和引用，不要为每个小步骤重复扫描。

## 1. 写入范围与 staging

只有本次任务本身包含知识写入时，才允许记录和写入：

- 用户明确要求创建或更新知识
- 本次代码变更涉及已被 wiki 记录的模块、行为、文件或配置（见第 4 节）
- 本次任务确认了新的、已核实的事实

没有上述情况时（包括纯读取、检索未命中、任务开始或结束、模块数量偏多、运行时预算提示），不创建 wiki、不写 staging、不合并、不做维护检查。不要为了触发一次审计而制造写入。

写入 staging 前还有一个硬性前提：`.wiki/skills` 必须已经存在。在未初始化的项目中，除用户明确要求初始化外严禁创建 `.wiki/` 目录，一律不写 `.wiki/staging.md`；所有待办、发现或阻塞点只能在对话回复中直接说明。只有当项目已接入且 `.wiki/skills` 存在、并且本次任务包含知识写入时，才允许记录到 `.wiki/staging.md`。

仅当写入路径成立且任务允许记录时，才把待办写入 `.wiki/staging.md`：

```
## [YYYY-MM-DD HH:MM] <简述>
<具体内容>
```

适合 staging 的内容：wiki 过时但当前任务不涉及；已发现的坑尚未解决；待确认的疑问；临时发现但不是本次重点；疑似应合并但无法确认真实关系或存在并发编辑；待验证的假设；PR 待合并后需要更新的内容；临时状态（不是当前代码的真实状态）。

每条注明涉及的领域，方便之后按相关性筛选。只处理与本次变更相关的条目：已确认、已有足够信息且不属于其他进行中任务的可以处理后删除，无关条目保持原样，不做全量清扫。

## 2. 查重与入口选择

写入前先对照现有条目的 `name` / `description`，找出同名、同源、同领域或描述范围明显重叠的候选。共享几个词只是候选线索，不能单独证明应该合并。优先更新或合并已确认合适的条目，而不是新增模块；条目少也不豁免这一步。

新模块只在确实没有合适入口时创建。

## 3. 完整核对候选

对每个候选都必须读取完整的 `SKILL.md` 正文和所在目录的支持文件，并核对当前代码，确认是否真的属于同一领域、是否值得更新或合并。不要凭 description 相似下结论：description 相似可能只是路由词重合，正文却记录了完全不同的行为、资源或约束。

## 4. 代码同步与内容真实性

wiki 记录的是此刻代码的真实行为，不是期望的最终状态。写入前先读代码确认，不要凭记忆写。

代码变更后，只同步与本次变更相关的知识：

1. 改了函数名 → 更新引用该函数的 wiki
2. 改了行为 → 更新描述该行为的 wiki
3. 删了文件 → 更新引用该文件的 wiki
4. 改了配置 → 更新描述该配置的 wiki

已核对代码、没有并发或所有权疑虑的例行同步和合并直接执行，不需要额外征求许可；没有相关代码变更或知识写入的任务不做同步。

不要把临时状态写进 wiki：待合并的 PR、待确认的行为、期望的最终状态都属于 staging；当前代码实际行为、已确认的坑和解决方案、已合并的变更才写进 wiki。

由于 wiki 只是代码的镜像而非真相，新建模块和本次触及的历史模块都必须在顶部一级标题下方带上第 9 节模板里的约束块，声明代码是唯一真相来源、使用前需核对当前实现。这样即使读取方直接通过原生 skill 链接打开该模块、没有加载 `superwiki/SKILL.md`，也不会把过时描述当成事实。

## 5. 条件化索引规模核对

只在 `name`、`description`、路径或条目清单可能变化时才比较改动前后的元数据索引。已经能拿到当前运行时的完整 skill 清单和预算信息时，直接用 `name` + `description` + 路径比较，不加载正文；拿不到时，只对本地 `.wiki/skills` 索引做估算，并明确说明全局状态未知。不要为此读取无关全局配置，也不要新增 runtime adapter、服务或 hook 来换取精度。

仅正文编辑且索引不变时，跳过全库预算重算，但仍要完成本文件第 2、3 节的相关条目一致性与重复检查，以及第 7 节的元数据校验。

## 6. 合并且不丢信息

确认合并后：

1. 选一个更概括、触发词更准确的名字
2. 合并 description，保留所有子主题、触发词和边界条件
3. 合并正文，只去重，保留所有独有事实、示例、资源文件（脚本、数据、图片等）和边界条件
4. 按第 7 节校验被写入的 `SKILL.md`
5. 按第 8 节更新引用并删除旧目录

不要为了降低数量而合并无关条目，不承诺仅靠合并文件能节省多少 token，也不设模块数量配额。

## 7. 全量写入校验

本批次中每一个被写入或被改名的输出都要校验，包括新建、普通编辑（含只改正文）、改名和合并结果，而不只是合并产物。用当前运行时或现有工具做真实解析：

- 用标准 YAML 解析器解析 `SKILL.md` 的 frontmatter；解析失败即视为未完成
- `name` 必须是字符串，长度 1..64，匹配 `^[a-z0-9]+(-[a-z0-9]+)*$`：仅小写 ASCII 字母和数字，单词之间用单个连字符，不得有前导、尾随或连续连字符
- 知识模块的 `name` 必须以 `wiki-` 开头，并且与所在目录名完全一致
- `description` 必须是字符串，原始解码字符串长度 1..1024 字符；纯空白（空格、换行、制表符）视为无效
- 新建或改名时，在可用的相关索引里确认最终采用的名字没有重名；不要为了这件事单独扫描全局条目
- 该输出中所有变更过的路径、`[[wiki-...]]` 引用和支持文件都必须真实存在
- 新建模块和本次触及的历史模块，正文顶部一级标题下方必须有第 9 节的约束块（代码是唯一真相来源，使用前核对当前实现）；缺失时补上再视为校验通过

这些长度与字符规则是运行时发现机制的标准格式限制，不是维护配额。不要引入任何额外的字数、行数、百分比或模块数量配额。

不安装新依赖，不新增校验服务或脚本。现有解析器不可用时，明确报告"元数据校验缺失"，不要声称成功，也不要删除任何源模块；不要用占位检查器冒充校验。校验未通过时先修正输出；无法修正就按第 10 节停下并说明。

## 8. 更新引用后再删除

顺序固定，任何一步未完成都不得删除旧目录：

1. 合并正文并迁移全部资源文件
2. 更新其他 wiki、文档和代码注释中所有 `[[wiki-...]]` 和路径引用
3. 用 grep 验证没有残留旧路径或旧链接
4. 确认旧目录没有未迁移的独有内容

## 9. 命名、description 与模板

### 命名

先看是否已有同领域模块：能更新或合并就不新建。名字只用小写 ASCII 字母、数字和单个连字符，以 `wiki-` 开头且与目录名一致。带日期的名字只用于确实独立、需要按时间区分的话题，不要按任务或日期机械增殖。

| 类型 | 命名格式 | 示例 |
|------|----------|------|
| 技术点 | `wiki-<技术点>` | `wiki-csv-encoding` |
| 模块 | `wiki-<模块名>` | `wiki-domain-status` |
| 规则 | `wiki-rule-<规则名>` | `wiki-rule-u08` |
| 修复 | `wiki-fix-<简述>-<日期>` | `wiki-fix-status-map-20260611` |
| 决策 | `wiki-decision-<简述>` | `wiki-decision-use-python` |

新建模块统一使用 `wiki-<topic>`，保证 OpenCode、Claude Code、Cursor 和 Codex/agent-compatible 路径都能识别。

### description

description 是原生发现索引，不是知识正文。它要说清三件事：这个条目讲什么、什么任务该用它、必要的边界（不覆盖什么、何时不适用）。触发信息尽量前置，包含任务里会出现的术语，让 agent 只看元数据就能判断。

正文才承载具体事实：路径、函数名、状态码、配置项、示例代码、操作步骤。不要把正文细节塞进 description，也不要靠扩大正文搜索范围或堆砌无关关键词来弥补索引问题。

示例：

```yaml
---
name: wiki-domain-status
description: |
  域名状态映射：状态含义、映射来源与 label_map 的正确用法。
  需要解释状态展示、排查状态映射错误时使用。
  边界：只覆盖当前代码里的状态枚举，不含前端文案与历史版本。
---
```

多行 description 必须使用 `description: |` 并按模板缩进续行。写成 `description: 第一行` 后跟顶格列表项会让 frontmatter 解析失败，条目从索引中消失。

### 模板

```markdown
---
name: wiki-<topic>
description: |
  <这个条目讲什么>
  <什么任务该用它>
  <必要的边界>
---

# 标题

> 约束：代码是唯一真相来源。使用本文内容前需核对当前实现，冲突时以代码为准。

## 快速参考

| 项目 | 说明 |
|------|------|
| ... | ... |

## 详细内容

...

## 相关知识

- [[wiki-<related>]] - 说明
```

正文保持简洁，相关主题优先合并进同一模块，不要过度拆分；跨条目引用用 `[[wiki-<name>]]`。维护时只做与本次写入相关的工作，不为凑数量而拆分或合并。

每一个 `wiki-*` 模块都必须把上面的约束块原样放在顶部一级标题（`# 标题`）的正下方，位于任何其他章节之前。原因：宿主运行时（Cursor、Claude Code、OpenCode、Codex/agent-compatible）通过原生 skill 链接直接发现 `wiki-*`，读取的 agent 会直接打开该主题的 `SKILL.md`，而不会先加载 `superwiki/SKILL.md`；这行约束保证它即使完全绕过 `superwiki` 的写入协议，也不会把过时文档当成事实来源。约束块是正文的一部分，不放进 frontmatter，也不影响 YAML 解析。

## 10. 历史遗留与停机条件

历史遗留的 `wiki_<topic>` 目录可以继续读取和维护，也可以读取而不修改；但不把下划线命名当作新的默认约定，也不要新建下划线命名的模块。被本次写入触及的输出必须符合当前格式（第 7 节）。

如果遗留条目需要改名、迁移资源或调整引用才能符合当前格式，且这属于本次任务授权的写入范围，就完成第 6、7、8 节的全部步骤；否则把它作为具体阻塞点报告（仅在满足第 1 节前提时才写入 staging），不要静默放过无效元数据，也不要顺手批量迁移无关条目。不要假设目录名可以替代 `name`，也不要把它当作所有运行时的通用发现依据。

遇到以下情况停下，不要自行猜测或强行删除：

- 语义冲突：wiki 说 A，代码做 B，无法判断哪个是期望状态
- 大范围重构：wiki 需要大改，但改动边界不清
- 历史决策与代码方向不一致
- 某个条目可能过时，但删除价值存疑
- 删除、合并或其他任务/其他人正在改同一批文件

询问要给出具体证据，例如：

```
wiki `wiki-xxx` 记录的内容和当前代码不一致：
- wiki 说: ...
- 代码实际: ...
以哪个为准？还是这个条目已经废弃可以删除？
```

允许停下时，若项目已初始化且 `.wiki/skills` 存在，可把具体阻塞点写入 staging；未初始化项目或纯读取任务只能在回复中直接说明，除用户明确要求初始化外严禁创建 `.wiki/` 目录，也严禁写 staging；不要编造结论。
